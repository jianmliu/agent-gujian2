# 多怪物与并行遭遇

沿用用户批准的批次范围：同怪唯一仲裁、两人分别交战、两场计时中途恢复、每场单次结算。固定试炼区增加第二只一次性怪物；不新增刷新、组队共斗、奖励或死亡规则。

## 状态与身份

v4 将单个 monster/battle 改为 monsters/battles 字典。固定怪物实例 trial-1 保留原中央位置，trial-2 位于同一区域内经原生物理检查的可达短直线路径末端。两只怪复用 shared_trial 内容定义，各自拥有唯一名字和公开状态。每场新战斗分配 UUID，并在怪物记录保留该 ID，结算后作为墓碑保留。敌人内容 ID 不再充当战斗 ID。

每名玩家最多拥有一场活动战斗，每只怪最多拥有一场活动战斗。战斗记录其 owner、monsterId、原生 combat 和绝对 tick 时钟。私有视图只返回本人的 battle，公开 monsters 显示所有怪物的位置、名字、占用和单次结算计数。请求必须同时匹配当前玩家和战斗 UUID。

## 推进与持久化

每个 50ms 世界步依稳定怪物顺序推进所有活动战斗，再轮换玩家顺序处理移动和扫掠接触。单次接触多个候选时按路径最早相交者、再按怪物 ID 仲裁。接触已占用怪物不阻挡探索。各玩家用独立原生引擎实例执行战斗，共用静态资源但不共用可变战斗上下文。

每步全部战斗、队伍、位置和怪物结果以同一 SQLite CAS 提交；任意写入失败均不发布候选状态，停止宿主并等待恢复。成功结算只删除对应战斗并标记对应怪物。另一场继续计时。重启恢复剩余模拟 tick、原 battle ID、双方私有状态，不补服务停止期间时间，不恢复移动租约。

## 迁移与校验

v1/v2/v3 先按原规则校验，旧中央怪及待决战斗迁为 trial-1，第二只为 available。v3 保留全部计时与战斗效果；v1/v2 缺少战斗时钟时使用原先迁移规则。迁移立即以 revision+1 的 CAS 原子写入，新 UUID 在启动返回前持久化，保留角色意图序号、位置、队伍与结算。资产/身份配置摘要继续兼容旧档，v4 验证固定怪物集合、battle/monster 双向关系、唯一 owner、唯一 ID、计数、时钟及原生敌方状态。损坏档拒绝启动。

## 界面与验收

地图与 Three.js 页均展示两只独立怪物和状态，自己的战斗面板显示目标名字。沿用真实移动接触与冷却按钮，无测试按键注入引擎。定点测试覆盖同 tick 仲裁、两场时钟隔离、串场/旧请求拒绝、同时命中的原子写失败、两场恢复与分别结算、活动/已结算旧档迁移、损坏关联拒绝。两浏览器在两个入口各跑完整路线，强制 SIGKILL 恢复待决双战斗，先结算一场并继续探索，再结束另一场，第二次重启仍各结算一次。原有 normal/pure 各15项保留。
